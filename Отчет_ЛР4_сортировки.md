## 1\. Цель работы

Реализовать и проверить алгоритмы Merge Sort, Counting Sort, Radix Sort LSD и Heap Sort, сопоставить их с Quick Sort из ЛР № 3 и встроенной сортировкой Python `sorted()`. Исследовать влияние размера массива, распределения данных и диапазона ключей на время выполнения.

## 2\. Реализованные алгоритмы

**Merge Sort.** Рекурсивно разбивает массив на две части, сортирует каждую и сливает упорядоченные половины. Для равных ключей выбирает элемент из левой части, поэтому реализация устойчивая. Исходный массив не изменяется.

**Counting Sort.** Для целых ключей от `0` до `key\_max` подсчитывает частоты, строит префиксные суммы и расставляет элементы в новый массив справа налево. Обратный проход сохраняет порядок равных ключей. При большом диапазоне ключей расход памяти становится чрезмерным.

**Radix Sort LSD.** Обрабатывает десятичные разряды от единиц к старшим. На каждом разряде применяет устойчивую сортировку подсчётом с десятью счётчиками. Устойчивость обязательна: при обработке старшего разряда должен сохраняться порядок по уже обработанным младшим разрядам.

**Heap Sort.** Строит max-кучу снизу вверх с помощью `sift\_down`. Далее переносит максимум в конец активной части и восстанавливает свойство кучи. Работает на месте, без дополнительного массива.

**Quick Sort.** Выбирает случайный опорный элемент и делит значения на меньшие, равные и большие. Рекурсивно сортирует две крайние части; использование дополнительной памяти связано с созданием списков и конкатенацией. Случайный выбор опоры снижает вероятность неблагоприятных разбиений, но не исключает худший случай.

**`sorted()`.** Встроенная эталонная сортировка Python, используемая для проверки корректности и сравнения времени.

## 3\. Оценка сложности и свойств

Обозначения: `n` — длина массива, `k = key\_max + 1` — число возможных значений ключа, `d` — число десятичных разрядов максимального числа.

|Алгоритм|Лучший случай|Средний случай|Худший случай|Доп. память|Устойчивость|Ограничения|
|-|-|-|-|-|-|-|
|Merge Sort|O(n log n)|O(n log n)|O(n log n)|O(n)|Да|Нужен сравнимый ключ|
|Counting Sort|O(n + k)|O(n + k)|O(n + k)|O(n + k)|Да\*|Только целые ключи `0…key\_max`; большой k затратен|
|Radix LSD|O(d(n + 10))|O(d(n + 10))|O(d(n + 10))|O(n + 10)|Да\*|Неотрицательные целые числа|
|Heap Sort|O(n log n)|O(n log n)|O(n log n)|O(1)|Нет|Сортирует исходный список|
|Quick Sort (трёхчастное разбиение)|O(n) при всех равных значениях|O(n log n) ожидаемо|O(n²)|O(n) типично; до O(n²) в худшем случае|Не гарантирована в общем случае|Случайные опоры, дополнительные списки|
|Python `sorted()`|O(n)|O(n log n)|O(n log n)|O(n)|Да|Встроенная реализация Python|

\* Устойчивость для одинаковых ключей обеспечивается обратным проходом. В текущем коде сортируются целые числа; различимость объектов с равными ключами для Counting/Radix непосредственно не проверяется.

**Обоснование.** При слиянии каждый элемент помещается в результат один раз: O(n + m) для двух списков. У Merge Sort O(log n) уровней рекурсии и O(n) операций слияния на каждом уровне. Counting Sort выполняет линейные проходы по массиву и диапазону ключей. Radix Sort повторяет подсчёт для каждого из d разрядов. Heap Sort строит кучу за O(n), затем выполняет до n просеиваний по O(log n). Quick Sort в среднем делит массив на достаточно сбалансированные части, но может получить крайне неравномерные разбиения.

## 4\. Методика измерений

Использованы размеры `n = 1 000, 3 000, 10 000, 30 000, 100 000`. Для каждого размера сгенерированы пять распределений: случайные значения в широком диапазоне, в узком диапазоне, отсортированные, обратно отсортированные и почти отсортированные значения (около 1% случайных обменов).

Каждый алгоритм прогревался одним запуском, после чего выполнялось пять измерений времени через `time.perf\_counter()`. В таблицы внесена медиана пяти измерений. Каждый запуск получал свежую копию входных данных. `Counting Sort` пропускалась для широкого диапазона до 10⁹, поскольку массив счётчиков был бы непрактично велик. Измерения получены в среде выполнения этой работы и могут отличаться на другом компьютере.

**Ограничение воспроизводимости:** функция `quick\_sort` при отсутствии аргумента `rng` создаёт собственный `random.Random()` без фиксированного seed. Поэтому для Quick Sort порядок выбора опор в текущем бенчмарке не полностью воспроизводится одним глобальным `random.seed(seed)`. Для строгой повторяемости следует передавать `random.Random(seed)` явно при каждом замере.

## 6\. Анализ результатов

Графики построены в логарифмическом масштабе по обеим осям. С ростом n время алгоритмов, как правило, увеличивается, но отдельные точки могут отклоняться от гладких теоретических зависимостей.

* При `n = 100 000` для распределения **случайные числа, узкий диапазон** минимальное измеренное время было у **sorted()** (0.008082 с); максимальное — у **Heap Sort** (0.288245 с).
* При `n = 100 000` для распределения **случайные числа, широкий диапазон** минимальное измеренное время было у **sorted()** (0.013718 с); максимальное — у **Heap Sort** (0.340555 с).
* При `n = 100 000` для распределения **отсортированный массив** минимальное измеренное время было у **sorted()** (0.000318 с); максимальное — у **Heap Sort** (0.312783 с).

**Влияние распределения.** Для `sorted()` уже упорядоченные и почти упорядоченные последовательности могут обрабатываться эффективнее благодаря адаптивному поведению встроенного алгоритма. Merge Sort и Heap Sort сохраняют асимптотическую оценку O(n log n) при всех рассмотренных распределениях. Quick Sort со случайной опорой уменьшается риск систематически плохих разбиений на упорядоченном вводе, но реальное время дополнительно зависит от числа повторяющихся ключей.

**Влияние диапазона.** Counting Sort выгодна, когда k мало относительно n. При `key\_max = 10⁹` массив счётчиков должен иметь примерно миллиард элементов, поэтому измерения для `random\_wide` не проводились. При небольшом диапазоне счётчики компактны и алгоритм выполняет линейные проходы.

**Почему измерения расходятся с асимптотикой.** Нотация O описывает скорость роста затрат при увеличении n, но не абсолютное время. На результат влияют накладные расходы интерпретатора Python, выделение памяти, рекурсивные вызовы, кэширование, фоновая нагрузка, случайный выбор опоры и точность таймера. Поэтому на отдельных размерах возможны пересечения кривых.

## 7\. Проверка корректности

После исправления размера `count` в Counting Sort встроенная `self\_check()` завершилась сообщением **`self\_check: OK`**. Проверены пустые и одноэлементные массивы, массив равных элементов, стабильность Merge Sort по парам `(ключ, порядковый номер)` и 200 случайных наборов с сопоставлением результатам `sorted()`. Для Heap Sort проверено изменение исходного списка на месте.

Важно: `self\_check()` не содержит полноценной проверки стабильности Counting Sort и Radix Sort на различимых объектах с одинаковыми ключами. Устойчивость этих реализаций следует из структуры алгоритма и обратного прохода при расстановке.

## 8\. Вывод

В работе реализованы и проверены пять алгоритмов сортировки, а также выполнено сравнение с `sorted()`. Merge Sort обеспечивает предсказуемое время O(n log n) и устойчивость. Heap Sort имеет ту же асимптотику и требует O(1) дополнительной памяти, но не является устойчивой. Counting Sort подходит для небольшого диапазона целых ключей; Radix Sort эффективно использует подсчёт по десятичным разрядам. Рандомизированный Quick Sort в среднем работает за O(n log n), однако худший случай остаётся квадратичным. Практический выбор алгоритма зависит не только от асимптотики, но и от диапазона ключей, распределения данных, требований к памяти и устойчивости.
